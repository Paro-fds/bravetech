# US-023: Migrations de base de données avec Alembic

**Status:** ✅ Done
**Milestone:** Epic 5 — Mise en production
**GitHub Issue:** [#40](https://github.com/Paro-fds/bravetech/issues/40)

---

## En tant qu'Administrateur
Je veux que chaque évolution du schéma de la base s'applique automatiquement et sans perte au déploiement
Afin que les dossiers déjà reçus survivent à chaque nouvelle version du portail.

## Contexte
`backend/main.py` crée les tables au démarrage avec `Base.metadata.create_all` (« pas encore de migrations Alembic »). `create_all` crée les tables manquantes mais **ne modifie jamais une table existante** : la première story qui ajoute ou change une colonne casserait la production (E5-6, [epic-005-refinement.md](epic-005-refinement.md)). `backend/scripts/seed_admin.py` appelle aussi `create_all`.

**Bug constaté le 2026-11-04 sur la VM :** `requirements.txt` déclare `sqlalchemy>=2.0.0` sans borne haute. L'image Docker a installé SQLAlchemy **2.1.8**, dont le pilote PostgreSQL par défaut pour `postgresql://` est psycopg 3. L'image n'a que `psycopg2-binary` : le backend plante au démarrage (`ModuleNotFoundError: No module named 'psycopg'`). La CI et le développement utilisent SQLite, d'où un bug invisible jusqu'au premier lancement réel. Contourné sur la VM par un `docker-compose.override.yml` non versionné (`postgresql+psycopg2://…`).

Workstream : transverse (`dal/`, déploiement).

## Critères d'acceptation
- [ ] Le backend démarre sur PostgreSQL avec l'image Docker construite depuis le dépôt, sans contournement : pilote explicite et versions des dépendances Python figées (pas de `>=` sans borne haute pour SQLAlchemy et le pilote).
- [ ] Alembic est configuré dans `backend/` ; la migration initiale reproduit exactement le schéma actuel (`candidats`, `candidatures`, `documents_soumis`, `utilisateurs`, et les autres tables existantes).
- [ ] Les migrations s'appliquent avant le démarrage de l'API (`alembic upgrade head`) ; `create_all` n'est plus appelé en production.
- [ ] Une base déjà créée par `create_all` (comme celle de la VM) est adoptée sans perte (`alembic stamp` documenté ou détecté).
- [ ] Un test vérifie que les modèles SQLAlchemy et la dernière migration ne divergent pas (autogenerate vide).
- [ ] `tests/unit/test_architecture.py` reste vert : Alembic vit dans `dal/`/infrastructure, jamais dans `entities/`.

## As-built notes

**2026-11-04 — implémentation (branche `feat/us-023-alembic`).**
- **Pilote : psycopg2 gardé**, pas de passage à psycopg 3 (hors périmètre, et psycopg2 tourne déjà sur la VM). `backend/dal/database.py` réécrit `postgresql://` et `postgres://` en `postgresql+psycopg2://` (`normaliser_url`), et `docker-compose.yml` donne l'URL explicite : le `docker-compose.override.yml` de la VM devient inutile.
- **Versions figées** avec `==`, celles de l'image qui tourne sur la VM depuis le 2026-11-04 (SQLAlchemy 2.1.8, FastAPI 0.162.0…), plus Alembic 1.20.1. `requirements-dev.txt` figé aussi (pytest 9.1.1, httpx 0.28.1).
- **Alembic** : `backend/alembic.ini`, `backend/dal/migrations/` (`env.py`, gabarit en français), révision `0001_schema_initial` générée par autogenerate sur une base vide puis relue. Les index passent par `op.create_index` plutôt que par le mode batch propre à SQLite. Les contraintes sans nom restent sans nom, comme avec `create_all`, pour que la base de la VM corresponde exactement.
- **Démarrage** : `backend/scripts/migrer.py`, lancé par le `CMD` du `Dockerfile` avant uvicorn (`sh -c "… && exec uvicorn …"`). Le `lifespan` de `main.py` est supprimé. `seed_admin.py` appelle `mettre_a_jour_schema` (sans effet si la base est à jour).
- **Écart avec la story : adoption automatique** plutôt qu'un `alembic stamp` manuel. `backend/dal/schema.py` détecte une base créée par `create_all` et la marque à `0001`. **Garde-fou ajouté** en cours de route : en copiant la vieille base de développement (`bravetech.db`), on a vu qu'elle contenait des tables d'avant ADR-008 (`cursus`, `documents_requis`) que `create_all` n'avait jamais supprimées. Une base ancienne à laquelle il manquerait une colonne aurait été déclarée à jour. L'adoption est donc refusée si une table ou une colonne des modèles manque ; une table en trop est tolérée.
- **Tests** : `tests/integration/test_migrations.py` (11 cas) : non-divergence modèles / migrations, adoption sans perte, table en trop tolérée, base trop ancienne refusée, relance sans effet, normalisation de l'URL. Vérifié à la main qu'une colonne ajoutée au modèle sans migration fait bien apparaître un écart. Suite complète : 326 tests verts.
- **Non vérifié** : PostgreSQL. La CI et le poste de développement n'ont que SQLite (pas de Docker local). La définition de terminé (base vide, puis base de la VM) reste à faire sur la VM.
- **GitGuardian (PR #48)** a signalé le mot de passe par défaut `fds_secret_pass` de `docker-compose.yml`. Il était là depuis US-004, mais a été réanalysé parce que la ligne `DATABASE_URL` a changé. Ce n'est pas le mot de passe de la VM (généré, dans `.env`), mais sans `.env` la production aurait tourné avec un mot de passe public. `POSTGRES_PASSWORD` est désormais obligatoire (`${POSTGRES_PASSWORD:?…}`) : sans lui, `docker compose` refuse de démarrer.
