# US-026: Déploiement continu vers la VM de la FDS

**Status:** 🔲 Backlog
**Milestone:** Epic 5 — Mise en production
**GitHub Issue:** [#43](https://github.com/Paro-fds/bravetech/issues/43)
**Depends on:** US-023 (migrations au démarrage), US-025 (frontend vérifié en CI)

---

## En tant qu'Administrateur
Je veux que chaque fusion validée sur `master` arrive en ligne automatiquement, avec un retour arrière possible
Afin que le portail soit toujours à jour sans manipulation manuelle sur le serveur, et qu'une mauvaise version se corrige en quelques minutes.

## Contexte
Cible : la VM du portail sur le Proxmox de la FDS, administrée en SSH (E5-1 ; adresse et port uniquement dans les secrets GitHub, jamais dans le dépôt public). Le portail y tourne déjà, lancé à la main (E5-9). Dokploy est installé mais non utilisé (E5-3). Le dépôt est public : pas de runner auto-hébergé (E5-4).

Chaîne retenue :
1. Fusion sur `master` → CI verte (backend + frontend).
2. Build des images `backend` et `frontend` sur GitHub, publication sur GHCR, étiquetées par le commit.
3. Connexion SSH à la VM avec une **clé dédiée** (secret GitHub), limitée par `command=` dans `authorized_keys` à un script de déploiement.
4. Le script tire les images de ce commit, relance le compose, vérifie que le portail répond ; en cas d'échec, revient à l'étiquette précédente.

`SOLUTION_DESIGN.md` décrit encore Railway et Vercel dans ses sections architecture, stack et déploiement, en contradiction avec ADR-006.

Workstream : transverse (déploiement).

## Critères d'acceptation
- [ ] Un workflow construit et publie les deux images sur GHCR à chaque push sur `master`, après les tests.
- [ ] Un compose de production utilise ces images (`image: ghcr.io/…:${TAG}`) au lieu de les construire, sans `container_name` ni mot de passe par défaut ; `.env.example` liste toutes les variables.
- [ ] Le déploiement passe par un environnement GitHub « production » (approbation manuelle activable par le Project Owner).
- [ ] La clé de déploiement ne peut lancer que le script (`command=`, `no-port-forwarding`, `no-pty`).
- [ ] Le script vérifie la santé du portail après relance et revient à la version précédente en cas d'échec ; le résultat apparaît dans le journal du workflow.
- [ ] Un retour manuel à une version donnée est documenté (une commande).
- [ ] ADR « Déploiement » ajouté ou complété dans `SOLUTION_DESIGN.md §14`, et les sections Railway / Vercel alignées sur la VM Proxmox ; `GLOSSARY.md` (Frontend, Backend) corrigé.
