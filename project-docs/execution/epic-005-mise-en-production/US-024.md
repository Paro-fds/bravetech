# US-024: Adresse réelle du visiteur derrière les proxys

**Status:** ✅ Done
**Milestone:** Epic 5 — Mise en production
**GitHub Issue:** [#41](https://github.com/Paro-fds/bravetech/issues/41)

## En tant que Candidat
Je veux pouvoir suivre mon dossier même quand beaucoup d'autres candidats consultent le portail en même temps
Afin de ne pas être bloqué à cause des autres, pendant que ceux qui tentent de deviner des références restent freinés.

## Contexte
`backend/api/v1/limiteur.py` limite la consultation de dossiers (20 requêtes, US-009) et les envois par adresse IP. `adresse_client` lit le **premier** élément de `X-Forwarded-For` (E5-7, [epic-005-refinement.md](epic-005-refinement.md)).

En production, la chaîne est : visiteur → Apache UEH (TLS) → Nginx du conteneur frontend → FastAPI. Deux défauts :
- le premier élément de `X-Forwarded-For` est fourni par le visiteur : il peut l'inventer et contourner le limiteur ;
- si l'Apache UEH ne transmet pas l'adresse du visiteur, tous les candidats partagent la même adresse et le limiteur bloque tout le monde après 20 consultations.

Workstream : WS-03 (suivi), transverse (`api/`, `frontend/nginx.conf`).

## Critères d'acceptation
- [ ] L'adresse retenue est celle ajoutée par le dernier proxy de confiance (lecture depuis la droite de `X-Forwarded-For`, nombre de proxys de confiance configurable par variable d'environnement).
- [ ] Un `X-Forwarded-For` inventé par le visiteur ne change pas l'adresse retenue (test).
- [ ] Sans proxy (développement), l'adresse de la connexion est utilisée.
- [ ] La configuration attendue de l'Apache UEH (en-têtes transmis) est écrite dans la spec tech, et vérifiée sur la VM une fois la bascule faite.

## Hors périmètre
- Un limiteur partagé entre plusieurs processus (Redis) : un seul processus uvicorn en V1.

## As-built notes

**2026-11-04 — implémentation (branche `feat/us-024-adresse-visiteur`).**
- **Constat sur la VM avant le code** : les journaux Nginx montrent que l'Apache UEH transmet déjà l'adresse publique du visiteur dans `X-Forwarded-For`. Le second défaut de la story (tous les visiteurs partagent une adresse) ne se produit donc pas tant qu'Apache garde ce comportement. Le premier, l'en-tête inventé, était bien réel.
- **`adresse_client`** lit désormais `X-Forwarded-For` depuis la droite : la N-ième entrée, N = `TRUSTED_PROXY_COUNT` (variable d'environnement ; le nom n'était pas fixé par la story). Valeur par défaut `1`, le Nginx du conteneur, qui donne le même résultat qu'avant pour un accès direct. Sur la VM : `2`. Une valeur invalide retombe sur `1`.
- **Moins d'entrées que de proxys** (accès direct au port de la VM, sans Apache) : l'entrée la plus à gauche est retenue. Limite documentée dans la spec tech §5.2.
- **`frontend/nginx.conf` inchangé** : `$proxy_add_x_forwarded_for` ajoute l'adresse d'Apache sans effacer celle du visiteur, c'est le comportement voulu.
- **Tests** : `tests/unit/test_adresse_client.py`, avec des adresses fictives (RFC 5737) qui reproduisent la chaîne de la VM ; jamais les vraies adresses relevées dans les journaux, le dépôt est public : en-tête absent, une valeur, en-tête inventé, deux visiteurs distincts, sans proxy, valeur invalide. Le test existant `test_documents_api.py` (une adresse par `X-Forwarded-For`) passe sans changement.
- **Reste pour la définition de terminé** : mettre `TRUSTED_PROXY_COUNT=2` dans le `.env` de la VM, puis vérifier derrière l'Apache UEH, une fois son `ProxyPass` corrigé (aujourd'hui, seul `/` passe : l'API n'est pas joignable par le domaine).
