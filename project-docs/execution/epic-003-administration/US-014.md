# US-014: Notification email déclenchée par une décision admin

**Status:** ✅ Done  
**Milestone:** Epic 3 — Administration & Audit  
**GitHub Issue:** [#14](https://github.com/Paro-fds/bravetech/issues/14)  
**Depends on:** US-013 (Décision admin persistée), US-008 (Port IEmailSender disponible)

---

## En tant que candidat
Je veux recevoir un email immédiatement après qu'un administrateur valide ou rejette l'un de mes documents  
Afin de réagir rapidement — notamment pour remplacer un document rejeté sans perdre de temps.

## Contexte
Cette story finalise la boucle de communication entre l'administration et le candidat. L'email est déclenché dans le use case admin (`ValiderDocument` / `RejeterDocument`) via le port `IEmailSender` — le même adaptateur (ConsoleEmailSender en dev, ResendEmailSender en prod) que celui mis en place en US-008. L'envoi est **non-bloquant** : un échec email ne doit ni annuler la décision admin ni retourner une erreur HTTP à l'agent.

## Critères d'acceptation
- [ ] Après une validation admin, le candidat reçoit un email HTML indiquant le nom du document validé.
- [ ] Après un rejet admin, le candidat reçoit un email HTML indiquant le nom du document rejeté, le motif (si renseigné), et un bouton **« Remplacer le document → »** pointant vers `/suivi/{reference}`.
- [ ] Si l'envoi d'email échoue (timeout Resend, clé absente), la décision admin est tout de même enregistrée en base et l'API retourne 200 à l'agent — l'erreur est loggée côté serveur.
- [ ] En développement local sans clé Resend, le `ConsoleEmailSender` affiche l'email dans les logs serveur (aucune erreur levée).
- [ ] Les emails ne sont envoyés que si l'envoi est activé (variable d'env `EMAIL_ENABLED=true`).

## Hors périmètre
- Les notifications SMS (US-016 — Epic 4, Should Have).
- Les notifications email de soumission initiale (US-008 — déjà livré).

## As-built notes
**2026-11-01 — code écrit et vérifié sur un vrai serveur (mode console), aucun email réel reçu** (branche `feat/us-014-email-decision`, empilée sur US-013) :
- **Déclenchement** : la route `PUT /api/v1/admin/documents/{id}/statut` ajoute l'envoi en **tâche de fond, après l'enregistrement** de la décision (même mécanisme que la confirmation d'US-008). Une décision refusée (422 motif manquant, 409 déjà décidée) n'envoie rien.
- **Contenu** : validation → « Pièce validée — <pièce> (<référence>) », avec lien « Suivre mon dossier » ; refus → « Pièce à remplacer — … », avec le **motif** et un bouton **« Remplacer le document → »** vers `/suivi/<référence>`. Texte brut et HTML ; le HTML échappe le prénom et le motif (un test le vérifie).
- **Non bloquant** : toute exception d'envoi est absorbée et journalisée avec la référence, la pièce et le type d'erreur seulement (ni adresse, ni message brut). La réponse reste 200 et la décision reste en base (testé avec un envoi en panne).
- **`EMAIL_ENABLED`** : `false` (ou `0`, `no`, `non`) → plus aucun email, ni Resend ni mode console ; par défaut activé. Cela vaut aussi pour l'email de confirmation d'US-008 (même fabrique `creer_email_sender`). Ajouté à `docker-compose.yml` et `.env.example`.
- **Un email par décision** : un dossier de 5 pièces peut produire jusqu'à 5 emails si les pièces sont traitées une par une. C'est ce que demande la story ; un regroupement serait un autre choix de conception.
- **Limite connue** : le bouton « Remplacer le document → » mène à la page de suivi, qui n'offre pas encore de remplacement en ligne (il montre le motif et un lien « contactez la Faculté ») : le téléversement de remplacement est **US-010**. Tant qu'US-010 n'est pas faite, l'email promet un remplacement que le candidat ne peut pas faire seul.
- **Vérifié** : `pytest` (contenu, échappement, échec non bloquant et journal, interrupteur, email envoyé / non envoyé par l'API) ; parcours réel sur serveur lancé : le refus (avec motif et lien) et la validation sont écrits dans les journaux. **Non vérifié** : l'arrivée d'un vrai email chez un candidat (aucune clé Resend valide ni domaine vérifié), le rendu HTML dans une messagerie.
